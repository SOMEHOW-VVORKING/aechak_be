# SEARCH-T01 검색 기준 성능 재측정

2026-11-04에 AWS perf 스택에서 키워드 상품 검색 `GET /api/v1/search/products`의 개선 전 성능을 잰 기록이다. 단계마다의 판정은 같은 세션에서 잰 before와 after로 한다. T01과 누적 비교할 때는 기준 jar를 같은 세션에서 T01 기준 부하로 다시 재서 함께 비교한다. 지연은 ms, 요청률은 초당 HTTP 요청 수(req/s)다. run별 전체 표는 `SEARCH-T01.md`, 그래프는 `graphs/`의 SEARCH-T01 파일이다.

## 요약

- 개선 전 검색은 잰 어느 환경과 단계에서도 SLO(첫 페이지 p95 500ms 미만)를 지키지 못했다. kit가 낸 최대 안정 요청률은 측정층 10만 건, 운영 거울층 10만 건, 측정층 100만 건 모두 0이다. 10만 건은 T00 확인 run에서 0.25 req/s까지 내려가도 첫 페이지 p95가 720ms였다. 그래서 이후 단계는 ramp에서 처리 기준(실패율 1% 미만, dropped 0)을 통과한 가장 높은 단계(처리 가능 요청률)를 비교 부하로 쓴다.
- 측정층 10만 건은 측정한 단계 중 2 req/s를 처리하고 4 req/s에서 무너진다. 2 req/s에서 첫 페이지 p95가 780ms이고 4 req/s에서는 6.8초다. 2와 4 사이는 재지 않았다.
- 운영 거울층(dev와 운영의 `db.t4g.micro`)도 2 req/s 단계를 처리하지만 첫 페이지 p95가 1.9초로 측정층의 2.4배다. steady(1.4 req/s)에서는 첫 페이지 p95가 측정층의 1.6배이고 요청당 RDS CPU는 1.5배다.
- 측정층 100만 건은 측정한 단계 중 0.25 req/s를 처리하고 0.5 req/s에서 무너진다. 부하가 거의 없어도 첫 페이지 하나가 6초에서 9.5초 걸린다. 상품이 10배인데 등급별 대표 요청의 첫 페이지 지연은 12배 안팎이다.
- 필터 없는 기본 경로는 셀러 인덱스를 거쳐 상품 거의 전부를 읽는다. 일치하는 상품이 없는 검색어도 10만 건에서 목록 쿼리 262ms와 COUNT 249ms를 쓴다. 첫 페이지 쿼리 경과 시간의 절반 가까이(47%)가 COUNT다.
- 근거는 DB CPU와 쿼리 작업이 이 부하의 주된 병목임을 가리킨다. 10만 건 포화 단계에서 RDS CPU가 89%(1분 지표 추정)이고 api 컨테이너 CPU는 30초 평균의 최대가 1 vCPU의 9.7%다.
- 2026-10-15 노트북 측정 뒤에 생긴 `ix_products_seller_id` 때문에 조인 순서가 바뀌었다. 옵티마이저가 sellers부터 읽고 셀러마다 이 인덱스로 상품을 찾는다. 같은 100만 건 인스턴스에서 products부터 읽게 하면 일치가 없는 검색어의 목록과 COUNT가 3배 빨라진다.

## 가설

- 검색 SQL이 2026-10-15 노트북 측정(`2026-10-15-baseline.md`) 때와 같으므로 비용 구조도 같다. COUNT가 첫 페이지 DB 시간의 절반쯤이고 일치하는 상품이 많은 검색어일수록 느리다. 맞았다.
- 측정층은 노트북보다 빠르고 운영 거울층은 비슷하거나 느리다. 거울층은 맞았고 측정층은 틀렸다. 같은 쿼리가 측정층에서도 노트북보다 대부분 1.5배에서 1.8배 느렸다(10만 건 사료 COUNT는 2.3배).
- `ix_products_seller_id`는 조인 순서를 바꾸지 않는다. 틀렸다.

## 변경 내용

검색 코드와 스키마는 바꾸지 않았다. jar는 T00 head `8b9454805771`(origin/develop `2e0a61ce`에 prometheus 지표와 관리 포트 허용만 더한 커밋)로 빌드했다. jar sha256 앞 8자리 `22eeed43`은 T00 run의 jar와 같다.

이번 run에서 드러난 kit 결함을 고쳤다.

- **100만 건 요청 타임아웃.** 100만 건은 첫 페이지 하나가 유휴 상태에서도 6초에서 9.5초라 10초로는 부하가 거의 없어도 실패가 난다. 100만 건만 30초(2026-10-15 측정과 같은 값)로 두고 env.txt `request_timeout`에 적는다. VU 상한과 시나리오 끝 대기(`gracefulStop`)도 이 값으로 잡는다.
- **CloudWatch 시각.** 러너가 TZ=Asia/Seoul이라 AWS CLI가 CloudWatch 시각을 +09:00으로 찍었다. 변형 끝의 완결 확인은 UTC 분과 비교해서 모든 run이 CW 미완으로 적혔다. CloudWatch 조회만 TZ=UTC로 돌린다. 10만 건 run은 받아 둔 csv로 다시 판정했고 모두 완결이었다.
- **spike 회복 판정.** 지연만 보던 회복 판정이 실패한 탐침도 회복으로 셀 수 있었다. 회복 창 안에 실패가 없어야 하고 탐침 시간(90초)이 끝난 뒤 들어온 응답으로는 판정하지 않는다. T01 수치는 바뀌지 않았다.
- **거울층 manifest.** 거울층은 10만 건 기준 스냅샷에서 복원하므로 10만 건 manifest와 비교한다. 거울층 run의 행 수와 CRC는 10만 건 manifest와 같았다.
- **그 밖.** smoke도 같은 `gracefulStop`을 쓴다. explain은 products를 읽는 문장만 고른다(api의 검수 배치 쿼리가 섞여 들어왔다). 크레딧 패널은 5분 간격 지표가 run 하나에 점 하나라 선이 그려지지 않아 점을 찍는다. 그래프 도구의 spike 회복선을 요약 표와 같은 규칙으로 맞췄다.

- 데이터는 결정적 시드(`seed.sql`)다. 10만 건은 노출 상품 96,000건이고 검색어 일치 수는 강아지 47,000, 사료 10,000, 관절 2,667, 한정판 100, 없는상품 0이다. 100만 건은 각각 10배다. 10만 건의 products는 데이터 19MB와 인덱스 14MB라 거울층 버퍼 풀에도 들어간다.
- 운영 거울층은 측정을 시작하고 6분 안에(09:45 지표) CPU 크레딧이 바닥났다. 그 뒤로는 unlimited 초과분으로 돌아 초과 크레딧이 최대 13.8까지 쌓였고(10:05 지표) 측정 뒤 유휴 시간에 갚아 12:15 지표부터 0이다. `CPUSurplusCreditsCharged`는 09:30부터 인스턴스를 멈춘 13:45 지표까지 모두 0이다. 근거는 CloudWatch 5분 지표를 받은 `SEARCH-T01-mirror-credits.csv`다. unlimited 모드라 크레딧이 바닥나도 CPU가 깎이지 않으므로 셀은 유효하다(kit README의 거울층 규칙).
- 셀은 kit 버전 2다. ramp는 2 req/s부터 45초씩 두 배로 올리고 처음부터 처리하지 못하면 1, 0.5, 0.25 req/s로 내려간다. 100만 건은 0.125 req/s를 더했다. steady는 기준 요청률의 0.7배로 3분씩 세 번, spike는 3배를 30초 보낸 뒤 탐침을 90초 보낸다.

steady는 처리 가능 요청률의 0.7배(10만 건 1.4 req/s, 100만 건 0.175 req/s)를 요청해서 돌았다. 세 층 모두 실패와 dropped가 0이고 Hikari 대기도 0이다.

```
-> Limit: 21 row(s)  (actual time=477..477 rows=21 loops=1)
  -> Sort: case when (ps1_0.review_count is null) then 0 else ps1_0.review_count end DESC, p1_0.id DESC, limit input to 21 row(s) per chunk
    -> Nested loop left join ...  (actual time=0.151..428 rows=47000 loops=1)
      -> Nested loop inner join  (actual time=0.135..269 rows=47000 loops=1)
        -> Filter: (s1_0.status = 'ACTIVE')  (rows=990)
          -> Table scan on s1_0  (rows=1000)
        -> Filter: (inspection_status, sale_status, lower(p1_0.name) like '%강아지%')  (rows=47.5 loops=990)
          -> Index lookup on p1_0 using ix_products_seller_id (seller_id=s1_0.user_id)  (rows=100 loops=990)
      -> Single-row index lookup on c1_0, p2_0, p3_0 using PRIMARY  (loops=47000 each)
      -> Single-row index lookup on ps1_0 using PRIMARY  (loops=47000)
```

- 옵티마이저는 sellers 1,000행을 전부 읽은 뒤 셀러마다 `ix_products_seller_id`로 상품 100건을 찾는다. 2026-10-15 노트북 측정은 활성 카테고리에서 출발해 `category_id` 인덱스로 상품을 찾았다. 100만 건도 같은 계획이다.
- sellers부터든 categories부터든 상품 거의 전부를 보조 인덱스를 거쳐 하나씩 클러스터 인덱스에서 다시 읽는다. 그 뒤 일치한 47,000건마다 카테고리 세 번과 상품 통계 한 번을 PK로 조회하고 전부 정렬해 21건을 고른다.
- COUNT도 같은 계획을 따른다. 없는상품도 목록과 COUNT가 각각 250ms 안팎이라 상품 거의 전부를 읽는 비용이 바닥이다. 100만 건에서는 이 바닥이 3초다.

### 조인 순서 비교

100만 건 변형과 equiv가 끝난 뒤 15:15부터 15:17까지 러너가 같은 인스턴스에서 인기순 첫 페이지 쿼리를 세 가지 조인 순서로 EXPLAIN ANALYZE 세 번씩 돌렸다(유휴 상태, ms, 세 번의 범위). 현재 계획, `IGNORE INDEX (ix_products_seller_id)`, `STRAIGHT_JOIN`으로 products부터 읽기다. SQL은 `SEARCH-T01-joinorder.sql`, 결과는 `SEARCH-T01-joinorder-1m.txt`다.

| 검색어 | 쿼리 | sellers부터(현재) | seller 인덱스 무시(categories부터) | products부터 |
|---|---|---|---|---|
| 강아지 | 목록 | 5,814에서 5,927 | 5,253에서 5,327 | 5,237에서 5,315 |
| 강아지 | COUNT | 5,136에서 5,223 | 4,624에서 4,681 | 4,570에서 4,661 |
| 없는상품 | 목록 | 3,139에서 3,167 | 2,804에서 2,823 | 1,048에서 1,061 |
| 없는상품 | COUNT | 3,037에서 3,128 | 2,702에서 2,750 | 902에서 903 |

- seller 인덱스를 막으면 옵티마이저는 2026-10-15처럼 categories부터 읽고 이 인스턴스에서는 현재 계획보다 10% 안팎 빠르다. 노트북에서는 같은 비교를 하지 않았으므로 이 값으로 노트북과 AWS의 차이를 조인 순서와 환경으로 나누지는 않는다.
- products를 클러스터 인덱스 순서로 한 번에 읽으면 일치가 없는 검색어는 3배 빨라진다. 일치가 47만 건인 강아지는 10% 남짓 빨라진다. 상품 100만 건을 읽고 이름으로 거르는 데 1.1초이고 나머지 4초 남짓은 일치한 47만 건마다 셀러, 카테고리, 상품 통계를 PK로 조회하고 정렬하는 시간이다. 검색 전용 쿼리(T03)가 products부터 읽게 만드는 쪽의 근거다.

## 해석

- **비용 구조.** 검색 조건이 `lower(name) LIKE '%검색어%'`라 B-tree 인덱스로 일치하는 상품만 골라 읽을 수 없다. 필터 없는 기본 경로는 상품 거의 전부를 보조 인덱스를 거쳐 다시 읽고 첫 페이지는 같은 일을 COUNT로 한 번 더 한다. 그래서 일치하는 상품이 없어도 비용이 바닥에 깔린다. 두 크기에서 대표 요청은 상품 수에 비례하는 것보다 조금 더 느려졌다(10배에 12배 안팎). 두 점만 재서 일반 법칙으로 보지는 않는다.
- **병목.** 10만 건 포화 단계(ramp 4 req/s)에서 RDS CPU 89%(1분 지표 추정), api 컨테이너 CPU 30초 평균 최대 9.7%, Hikari 대기 최대 10이다. 근거는 DB CPU와 쿼리 작업이 주된 병목임을 가리킨다. run별 서버 수치는 `SEARCH-T01-server.csv`에 있다. api CPU는 30초 rate를 5초마다 본 평균과 최대(코어 단위)다. 서버 p95는 30초 창 히스토그램 추정의 최대라 30은 가장 큰 버킷(30초)에 걸렸다는 뜻이다. Hikari 타임아웃은 Prometheus increase 추정이라 소수가 나온다. 버퍼 풀 디스크 읽기는 run마다 0건에서 17건이라 I/O 관측으로만 적는다.
- **과부하.** 처리 한계를 넘으면 성공하는 요청이 오히려 줄어든다. 10만 건 spike(6 req/s)에서 burst 요청의 58%가 실패했고 Hikari 대기가 51까지 쌓였다. 쿼리 타임아웃이 없어 클라이언트가 포기한 요청도 DB가 끝까지 처리하기 때문이다. 회복 시간(36초, 76초)은 실패 없는 탐침 창이 처음 회복 기준을 만족한 한 번의 관찰이고 서버에 남은 일이 모두 끝났다는 보장은 아니다.
- **환경 차이.** 측정층은 2026-10-15 노트북보다 같은 쿼리가 대부분 1.5배에서 1.8배 느리다(10만 건 사료 COUNT는 2.3배). AWS 100만 건에서 조인 순서만 2026-10-15처럼 되돌리면 10% 안팎 빨라졌지만 노트북에서는 같은 비교를 하지 않았다. CPU, 관리형 DB, 버퍼 풀 크기, 부하 생성 방식이 함께 바뀌었으므로 노트북 대비 차이를 원인별로 나누지 않는다. 운영 거울층은 steady에서 측정층보다 첫 페이지 p95가 1.6배 느리고 CPU 크레딧이 6분 안에 바닥난다. 운영과 같은 인스턴스에서 상품이 10만 건이면 개선 전 검색은 잰 단계 중 2 req/s까지만 처리했고 그때 첫 페이지 p95가 1.9초다.
- **2026-10-15와 달라진 것.** 노트북 Docker(MySQL CPU 2개, 메모리 1GB)에서 AWS 고정 성능 인스턴스로 바꿨다. `ix_products_seller_id`가 생겼고 조인 순서가 바뀌었다. 커밋은 develop 2e0a61ce 기준이고 검색 쿼리 코드는 같다. Hikari는 두 측정 모두 기본값 10이다. 2026-10-15의 대표 수치는 첫 페이지만 보낸 부하였고 이번에는 첫 페이지 57%, 필터 14%, 다음 페이지 29%의 혼합 부하다.

## 결정

- **지표(D2) 확정.** 대표 지표는 최대 안정 요청률이고 지금은 세 층 모두 0이다. 단계 비교는 처리 가능 요청률을 비교 부하로 쓴다(10만 건 2 req/s, 100만 건 0.25 req/s). steady 폭은 10만 건 3.8%, 거울층 7.2%, 100만 건 2.5%로 모두 15% 안이다. 이 폭은 세 추정값의 관찰 범위이지 신뢰구간이 아니다. p99는 run당 첫 페이지가 150건 안팎이라 가장 느린 두세 건이 정하므로 기록만 한다. 나빠 보이면 첫 페이지 1,000건 이상의 확인 셀로 다시 재서 판정한다. 요청당 RDS CPU는 추정치라 before 세 run의 범위를 허용 폭으로 쓴다. 100만 건의 작은 차이는 steady p95 대신 sequential 중앙값과 steady p50으로 보고 큰 차이만 판정한다. spike 회복 기준은 10만 건 929ms, 100만 건 11,811ms다.
- **다음 단계.** 검색 조건이 인덱스를 못 쓰고 COUNT가 첫 페이지 DB 시간의 47%다. 다음 단계(T02)는 가장 싼 개입인 쿼리를 그대로 두고 인덱스만 더하기를 검증하되 효과가 거의 없을 것으로 예측한다. 상품명 부분 문자열 조건 `lower(name) LIKE '%검색어%'`는 B-tree 범위 검색을 쓸 수 없어서 일치하는 상품만 골라 읽게 만드는 인덱스가 없다. 노출 조건 인덱스와 커버링 인덱스는 행당 읽는 양만 줄일 수 있으므로 none, rare 검색어와 최신순에서 0%에서 15%, 인기순 고일치 검색어에서 0%로 예측한다. FULLTEXT 인덱스는 쿼리가 MATCH를 쓰지 않으면 계획에 나오지 않는다.
- **DB 예측.** DB만으로 가면(T02에서 T06) 10만 건은 SLO를 지키게 되지만 100만 건은 최대 안정 요청률이 0에 머물 것으로 예측한다. 첫 페이지의 10%인 강아지가 47만 건을 정확히 세는 COUNT를 피할 수 없고 그 한 쿼리가 500ms를 넘기 때문이다. 이 예측을 공정하게 확인하려고 2 req/s 아래에서도 SLO를 찾도록 kit의 ramp를 고쳤다(측정의 한계 절). T06 끝에서 이 예측과 측정을 나란히 적는다.

## 측정의 한계

- **합성 데이터.** 상품명은 시드 번호에서 짧은 주기로 만든다. 일반 상품명은 120행마다 반복되고 3,000행 주기 안의 이름 조합은 123개다. 카테고리도 상품 뜻과 무관하게 식으로 정한다. 검색어 일치 비율을 통제하는 데는 맞지만 실제 상품명의 어휘, 중복, 셀러와 검색어의 상관을 대표하지 않는다. ES 도입을 결정하기 전에 상품명이 다양한 데이터로 민감도를 한 번 본다.
- **표본.** 100만 건 steady는 run마다 첫 페이지 20건 안팎이고 ramp와 spike는 변형마다 한 번이다. 처리 가능 요청률은 잰 단계 중 통과한 가장 높은 값이고 그 사이 요청률은 재지 않았다. 몇 % 수준의 차이는 이 표본으로 구분하지 않는다.
- **부하 모델.** 반복 하나는 첫 페이지 뒤 다음 페이지를 이어 보내는 검색 흐름이라 HTTP 요청률이 응답에 따라 달라진다. 검색어와 필터는 run마다 무작위로 골랐다. 다음 단계부터는 반복 순번으로 고정해 before와 after가 같은 순서로 요청하고 steady 세 run은 서로 다른 고정 순서를 쓴다. 짧은 run은 검색어와 흐름의 조합까지 고르게 들지 않으므로 실제 요청 구성과 함께 본다.
- **파생 지표.** 요청당 RDS CPU는 CloudWatch 1분 평균을 run의 요청 수로 나눈 추정치이고 RDS 전체 CPU를 포함한다. 다이제스트 비율은 상위 10개 문장의 경과 시간 비율이다.
- **환경 범위.** 같은 AZ 사설망에서 api를 직접 부른 백엔드 지연이다. ALB, TLS, 인터넷 구간, 여러 api 인스턴스는 없다. 데이터는 버퍼 풀에 올라간 상태다. performance_schema와 0.1초 slow log가 켜져 있고 그 부하는 따로 재지 않았다. 운영 거울층은 DB 인스턴스 등급만 운영과 같고 데이터와 트래픽은 측정층과 같다.
- **kit 결함.** 첫 단계(2 req/s)가 SLO만 못 지키고 처리 기준은 통과하면 더 낮은 요청률을 재지 않았다. 10만 건과 거울층의 최대 안정 요청률 0은 이 탐색을 거치지 않은 값이다. 다만 1 VU sequential에서도 강아지 첫 페이지 중앙값이 770ms와 1,188ms이고 10만 건은 T00 확인 run의 0.25 req/s에서도 p95가 720ms라 결론은 같다. 이후 변형을 위해 kit 버전 3에서 ramp를 고쳤고 바닥 단계는 반복이 20회 이상 들도록 늘렸다.
