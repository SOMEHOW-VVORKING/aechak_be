# 검색 성능 기준 측정 2026-10-15

키워드 상품 검색 `GET /api/v1/search/products`를 개선 전 상태로 잰 기록이다. 개선한 뒤 같은 조건으로 다시 재서 이 수치와 비교한다.

## 요약

- 병목은 MySQL CPU다. 초당 3건에서 api CPU는 평균 7%이고 MySQL은 2코어 중 평균 1.09코어를 쓴다. 디스크 읽기가 없어서 메모리에 올라온 상품을 CPU로 전부 읽는 비용이 응답 시간의 대부분이다.
- 검색어 조건 `lower(name) like '%검색어%'`는 인덱스를 쓰지 못한다. 요청마다 상품 전체를 읽고 쿼리 시간은 상품 수에 비례해 늘어난다.
- 첫 페이지 요청은 목록 쿼리와 전체 건수 COUNT 쿼리가 같은 범위를 따로 읽는다. COUNT가 DB 시간의 45~48%를 차지한다.
- 상품 10만 건에서는 초당 3건까지 p95 546ms로 안정적이다. 초당 4건부터는 요청 대부분이 10초 안에 응답하지 못한다.
- 상품 100만 건에서는 부하가 없어도 요청 하나에 4.0초에서 6.6초가 걸린다. 초당 0.2건에서 p95가 4.6초이고 초당 0.33건이면 DB가 포화된다.
- 처리 한계를 넘으면 성공하는 요청이 오히려 줄어든다. 상품 10만 건에서 초당 4건을 보내면 10초 안에 성공하는 요청은 초당 0.35건이다. 쿼리 타임아웃이 없어서 클라이언트가 포기한 요청도 DB가 끝까지 처리하기 때문이다.

수치는 노트북 Docker에서 잰 값이라 dev와 절대값이 다르다. 개선 전후를 같은 조건에서 비교하는 데 쓴다.

## 측정 환경

| 항목 | 설정 |
|---|---|
| 호스트 | 노트북 OrbStack, Docker 29.4.0, VM 10 vCPU와 메모리 16GB |
| MySQL | 8.4 컨테이너. dev RDS db.t4g.micro에 맞춰 CPU 2개, 메모리 1GB, 버퍼 풀 512MB로 제한한다 |
| api | `boot/api` jar를 Java 21로 실행한다. ECS 태스크에 맞춰 CPU 1개, 메모리 2GB로 제한한다. Hikari는 기본값이라 풀 크기 10, 연결 대기 30초다 |
| 부하 생성 | 호스트에서 k6 2.2.0을 돌린다. 도착률을 고정하고 동시 요청은 20개까지 허용한다. 요청 타임아웃은 10만 건에서 10초, 100만 건에서 30초다 |
| 스키마 | dev와 같이 Flyway와 ddl-auto update로 만든다. `products` 인덱스는 PK, `public_id` 유니크, `category_id` FK 세 개다 |

## 데이터

`seed.sql`로 만든다. 상품명을 정해진 단어 목록에서 조합해 만들기 때문에 검색어별 일치 비율이 측정마다 같다.

| 테이블 | 행 수 | 구성 |
|---|---|---|
| `sellers` | 1,000 | 30%는 기본 배송비 0원, 1%는 정지 상태 |
| `products` | 10만, 100만 | 판매중 93%, 품절 5%, 판매중지 2%, 검수 대기 1% |

| `categories` | 67 | 마이그레이션 시드 그대로 |

100만 건일 때 `products`는 데이터 182MB와 인덱스 65MB, `product_stats`는 41MB라 버퍼 풀에 모두 들어간다.

검색어는 일치 비율에 따라 다섯 등급으로 나눠 가중치를 두고 고른다.

| 등급 | 검색어 | 일치 비율 | 가중치 |
|---|---|---|---|
| high | 강아지 | 약 47% | 10 |
| mid | 사료, 연어, 간식 | 6~10% | 45 |
| low | 관절, 하네스, 바잇미 | 2.5~2.7% | 30 |
| rare | 한정판 | 0.1% | 10 |
| none | 없는상품 | 0% | 5 |

## 측정 방법

- 따로 적지 않으면 요청은 첫 페이지, 기본 정렬인 인기순, 필터 없음으로 보낸다. 로그인하지 않은 요청이다.
- 측정마다 MySQL에서 실행 중인 쿼리가 없어질 때까지 기다리고 `performance_schema` 다이제스트를 비운 뒤 시작한다.
- 3초마다 컨테이너 CPU와 MySQL `Threads_running`을 기록한다. `Threads_running`은 이벤트 스케줄러 때문에 유휴 상태에서도 2다.
- 시작 30초 뒤부터 p95가 15초를 넘으면 k6가 측정을 중단한다.
- 쿼리 하나의 시간은 유휴 상태에서 `EXPLAIN ANALYZE`를 두 번 돌려 두 번째 값을 쓴다.

| 초당 4건 | 190 | 초당 0.35건 | 81.6% | 10초 초과 | 10초 초과 | 10초 초과 | 198% | 30 |
| 초당 5건 | 193 | 초당 0.29건 | 85.0% | 10초 초과 | 10초 초과 | 10초 초과 | 198% | 32 |

각 측정은 90초다. MySQL CPU는 코어 2개 기준이라 200%가 상한이다. 실패는 모두 k6의 10초 타임아웃이고 서버 로그에는 오류가 없다. 초당 4건과 5건에서 보낸 요청이 목표보다 적은 것은 동시 요청 20개가 모두 응답을 기다리느라 k6가 새 요청을 보내지 못했기 때문이다.

### 초당 3건에서 등급별 응답 시간

| 등급 | p50 | p95 |
|---|---|---|
| high | 536ms | 637ms |
| mid | 333ms | 441ms |
| low | 305ms | 382ms |

일치하는 상품이 없어도 290ms가 걸린다. 응답 시간 대부분은 일치 여부와 관계없이 상품 전체를 읽는 데 쓰인다.

### 초당 3건에서 쿼리별 비용

| 쿼리 | 호출 | 평균 | 쿼리당 읽은 행 |
|---|---|---|---|
| 목록 | 271 | 184ms | 약 11.7만 |

요청 하나가 DB에서 쓰는 시간은 약 0.35초다. 초당 3건이면 1.05코어가 필요하고 측정한 CPU 1.09코어와 맞는다.

### 혼합 시나리오

첫 페이지 60%, 필터와 정렬 20%, 다음 페이지 넘기기 20%를 초당 2회 반복했다. 다음 페이지 넘기기는 한 번에 최대 두 페이지를 더 요청해서 실제 요청은 초당 2.84건이다. 필터와 정렬 요청은 낮은 가격순에 가격 범위를 걸고 절반은 중분류를, 30%는 무료배송을 함께 지정한다.

| 요청 종류 | p50 | p95 | p99 |
|---|---|---|---|
| 첫 페이지 | 340ms | 490ms | 543ms |
| 필터와 정렬 | 45ms | 396ms | 427ms |
| 다음 페이지 | 220ms | 374ms | 489ms |

90초 동안 257건을 보냈고 실패는 없다. MySQL CPU는 평균 94%다. 다음 페이지는 COUNT를 실행하지 않아서 첫 페이지보다 빠르다. 중분류를 지정한 필터 요청은 `category_id` 인덱스로 해당 카테고리 상품만 읽어서 COUNT가 평균 13ms이고 약 7,900행만 읽는다. 중분류가 없는 필터 요청의 COUNT는 평균 153ms로 첫 페이지와 비슷하다.

## 병목 분석

### DB CPU

초당 3건에서 api CPU는 평균 7%, 최대 24%다. MySQL은 평균 109%이고 초당 4건부터 198%로 상한에 닿는다. 100만 건 초당 0.2건 측정 3분 동안 버퍼 풀 읽기 요청 3.2억 건 가운데 디스크 읽기는 0건이라 I/O는 병목이 아니다.

### 인덱스를 쓰지 못하는 검색 조건

`ProductKeywordSearchQueryAdapter`는 상품명 조건을 QueryDSL `containsIgnoreCase`로 만든다. 생성되는 SQL은 `lower(name) like '%검색어%'`이고 앞에 와일드카드가 있어 B-tree 인덱스를 쓸 수 없다. 요청마다 상품 전체를 읽으므로 상품 수가 10배가 되면 쿼리 시간도 12~14배가 된다.

### 첫 페이지마다 두 번 읽기

`ProductKeywordSearchService`는 커서가 없는 첫 페이지에서 목록과 별도로 `countMatching`을 호출한다. 두 쿼리가 같은 조건으로 상품 전체를 따로 읽어서 COUNT가 DB 시간의 45~48%를 차지한다.

### 불리한 조인 순서

옵티마이저는 활성 카테고리 67개에서 출발해 `category_id` 인덱스로 상품을 찾는다. 상품 행을 보조 인덱스 순서로 하나씩 클러스터 인덱스에서 다시 읽기 때문에 상품 테이블을 PK 순서로 읽을 때보다 느리다. `STRAIGHT_JOIN`으로 상품부터 읽게 하면 아래처럼 줄어든다. 각 칸은 목록 쿼리와 COUNT 쿼리 시간이다.

| 검색어 | 상품 수 | 현재 | 상품부터 읽기 | 상품부터 읽기와 `lower()` 제거 |
|---|---|---|---|---|
| 없는상품 | 10만 | 146ms, 144ms | 69ms, 59ms | 58ms, 51ms |
| 사료 | 10만 | 175ms, 156ms | 125ms, 98ms | 108ms, 90ms |
| 강아지 | 10만 | 301ms, 235ms | 296ms, 237ms | 287ms, 226ms |
| 없는상품 | 100만 | 2,083ms, 1,890ms | 680ms, 598ms | 572ms, 498ms |
| 사료 | 100만 | 2,496ms, 2,199ms | 1,172ms, 1,019ms | 1,095ms, 913ms |
| 강아지 | 100만 | 3,632ms, 2,963ms | 2,964ms, 2,418ms | 2,853ms, 2,315ms |

`name` 컬럼의 콜레이션은 `utf8mb4_0900_ai_ci`라 `lower()` 없이도 대소문자를 구분하지 않는다.

### 일치한 상품마다 드는 비용

인기순 정렬 값은 `product_stats`에 있다. 일치한 상품마다 셀러와 상품 통계를 PK로 조회하고 일치한 상품 전체를 정렬해야 21건을 고를 수 있다. 강아지처럼 상품 절반이 일치하는 검색어는 이 비용이 커서 조인 순서를 바꿔도 100만 건 기준 18%만 줄어든다.

### 처리 한계를 넘었을 때

초당 4건에서 동시에 실행 중인 쿼리가 약 10개로 늘고 쿼리 하나의 평균 시간이 0.18초에서 2.9초로 늘어난다. 동시 쿼리 10개가 코어 2개를 나눠 쓰면 0.9초 정도여야 하는데 그보다 세 배 느리다. 동시 쿼리가 늘면 쿼리 하나의 CPU 비용도 늘어난다는 뜻이고 그래서 이론상 한계인 초당 약 5.7건보다 일찍 포화된다. 쿼리 하나의 비용이 늘어나는 원인은 이 환경에서 구분하지 못했다.

검색 쿼리에는 타임아웃이 없다. k6는 동시 요청을 20개까지만 보내는데 Hikari 대기는 30을 넘는다. k6가 10초에 포기하고 연결을 끊은 요청도 서버가 계속 처리한다는 뜻이다. 측정이 끝난 뒤에도 Hikari 대기가 20개 넘게 남아 있었다. 그래서 초당 4건을 보내면 10초 안에 성공하는 요청은 초당 0.35건뿐이다.

### 병목이 아닌 것

api CPU와 메모리는 여유가 있다. Hikari 풀 크기도 원인이 아니다. 풀을 늘리면 이미 포화된 DB에 동시 쿼리만 늘어난다.

## 개선 후보

| 후보 | 근거 | 기대 효과 | 확인할 점 |
|---|---|---|---|
| 첫 페이지 COUNT 비용 줄이기 | COUNT가 DB 시간의 45~48% | 첫 페이지 DB 시간 약 절반 감소 | 화면 명세는 결과 수를 1,240처럼 정확히 보여 준다. 상한을 두고 1,000+로 표시할지, 짧게 캐시할지, 목록 쿼리에서 함께 셀지 정해야 한다 |
| 조인 순서 고정 | 100만 건 없는상품 목록이 2,083ms에서 680ms로 감소 | 일치 비율이 10% 이하인 검색어에서 53~68% 감소 | `visibleProductQuery`는 다른 상품 목록도 쓴다. QueryDSL에서 옵티마이저 힌트를 넣을 수 있는지, 카테고리 조인 대신 활성 소분류 ID 목록으로 거르는 방식이 같은 효과를 내는지 확인해야 한다 |
| `lower()` 제거 | 콜레이션이 이미 대소문자를 무시함 | 조인 순서 고정 뒤 추가로 4~17% 감소 | `contains`로 바꿨을 때 와일드카드 이스케이프가 같은지 확인해야 한다. `SellerProductQueryAdapter`도 같은 조건을 쓴다 |
| 상품명 ngram FULLTEXT 인덱스 | 요청마다 상품 전체를 읽음 | 일치 비율이 낮은 검색어에서 크게 감소할 것으로 예상하지만 재지 않았다 | 두 글자 단위 토큰이라 한 글자 검색어 결과가 LIKE와 달라질 수 있다. 일치 상품이 많은 검색어에는 효과가 작다 |
| 인기순 정렬 키를 `products`에 두고 인덱스 생성 | 일치 상품이 많은 검색어는 일치한 상품마다 드는 비용이 큼 | 정렬 순서대로 읽다가 21건을 찾으면 멈출 수 있다. 재지 않았다 | 리뷰 수를 상품 행과 맞춰 갱신해야 한다 |
| 검색 쿼리 타임아웃 | 한계를 넘으면 성공 응답이 초당 0.35건으로 감소 | 과부하일 때 일부 요청만 실패하고 처리량은 유지 | 타임아웃 값과 클라이언트에 줄 오류 코드 |
| Elasticsearch | 위 방법으로 목표에 못 미칠 때 | | 인프라, 색인 동기화, 운영 비용 |

티켓에는 목표 수치가 없다. k6 스크립트는 첫 페이지 p95 500ms를 임시 목표선으로 표시한다. 상품 수와 처리량 목표를 정해야 Elasticsearch 전환 여부를 판단할 수 있다.
