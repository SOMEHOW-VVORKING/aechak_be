# 검색 성능 개선 시리즈 요약

상품 키워드 검색 API(`GET /api/v1/search/products`) 하나를 SEARCH-T01부터 SEARCH-T16까지 단계로 나눠 고치고 잰 기록을 모았다. 응답 계약(상품명 부분 일치, 카테고리와 가격 필터, 정렬 셋(인기순, 낮은 가격순, 최신순), 커서 페이지, 첫 페이지의 정확한 총개수)은 시리즈 내내 그대로다. 더한 것은 시간 초과 응답 503(40008) 하나다. 단계마다 근거와 재현 방법은 단계 보고서에 있다.

## 요약

- 상품 100만 건에서 MySQL 경로는 끝까지 SLO(인기순 첫 페이지 p95 500ms 미만)를 지키지 못했다. 인덱스, FULLTEXT, 총개수 쿼리 통합, 검색어별 경로 선택(T02부터 T06)으로 10만 건은 최대 안정 요청률이 0에서 32 req/s가 됐다. 100만 건은 2.8 req/s에서 첫 페이지 p95가 814ms에서 820ms였고 정확한 총개수 쿼리가 DB 시간의 69%였다. 같은 부하에서 Elasticsearch 어댑터(T07)는 p95 25ms였고 최대 안정 요청률이 256 req/s였다.
- 상품 1,000만 건에서 ES 튜닝(T10, 레버 다섯 개)은 고정 검색어 9개와 쓰기 없음 조건에서 첫 페이지 p95를 80ms에서 25ms로, 최대 안정 요청률을 32 req/s에서 64 req/s로 바꿨다. 초당 96건 순간 부하 p95는 15초에서 229ms가 됐다(순간 부하는 한 번씩).
- 상품 1,000만 건 최종 비교(T11)에서 최종 jar는 T07 jar보다 네 조건 모두 빨랐다. 같은 날 jar마다 새로 색인하고 같은 순서로 잰 첫 페이지 p95 중앙값이 고정 검색어 9개 169ms 대 17ms, 검색어 300개 313ms 대 64ms, 쓰기 초당 10건 171ms 대 24ms, 검색어 300개와 쓰기 142ms 대 39ms였다. 차이는 고정 검색어 9개에서 가장 크고(9.8배) 검색어 300개와 쓰기에서 가장 작았다(3.6배).
- ES 장애 때 DB만 읽는 요청을 지켰다. ES를 30초 멈춘 구간에 응답이 끝난 상품 상세 요청의 p95가 19.9초에서 21.1초였다. 검색이 ES를 기다리는 동안 DB 커넥션을 반납하지 않았기 때문이다. 기다리는 동안 커넥션을 반납하게 바꾸자(T13) 6ms에서 11ms가 됐다. ES 응답이 1초 늦을 때 검색 성공 비율은 4%에서 5%였던 것이 T16(동시 요청 상한, 연결 수 40, 시간을 넘긴 요청 취소 중단)으로 82%에서 85%가 됐다. ES 처리량을 넘는 초당 129건 순간 부하에서는 검색의 6.7%를 바로 거절하는 대신 순간 부하 30초 동안 상품 상세 p95가 693ms에서 87ms가 됐다.
- 상품 1억 건(T12)에서 튜닝 전 jar는 잰 요청률(0.25 req/s에서 2 req/s) 모두에서 실패율이 1%를 넘었다. 최대 안정 요청률 0은 통과한 요청률이 없다는 뜻이다. 튜닝한 jar는 2 req/s에서 SLO를 지켰다(첫 페이지 p95 3,013ms에서 286ms). ES 호스트는 r7g.xlarge(vCPU 4개, 메모리 32GB)에 ES 컨테이너 CPU 2개 제한이다.
- 확인한 요청에서는 검색 결과가 단계마다 같았다. 코드를 바꾼 단계마다 고정 요청 384개의 응답을 이전 단계와 비교했다(T10의 L3는 따로 비교하지 않았고 측정만 한 T08과 T12는 비교하지 않았다). T15에서 무작위 상품과 검색어로 JPA 어댑터와 ES 어댑터의 결과를 비교하는 테스트를 더했다.

## 측정 방법

- 측정은 별도 terraform 루트로 띄운 AWS perf 스택에서 했다. RDS db.m7g.large(MySQL 8.4), api m7i.large(api 컨테이너 1 vCPU, 2GB, Hikari 최대 10, Tomcat 최대 스레드 200), k6 러너 c7g.large, Elasticsearch 9.2.6 단일 노드(샤드 1개, 복제 0개, 힙 4GB)다. 지표는 Prometheus, Grafana, CloudWatch로 모았다.
- ES 호스트는 단계마다 둘 중 하나다. T07, T08, T10, T11, T16은 m7g.large(vCPU 2개, 8GB)이고 T12, T13, T14는 r7g.xlarge(vCPU 4개, 32GB)에 ES 컨테이너 CPU를 2개로 제한했다. 두 호스트의 절대값은 직접 비교하지 않는다(한계 절).
- 데이터는 결정적인 합성 시드다(셀러 1,000개, 상품의 60%에 리뷰 통계, 30%에 진행 중 할인). 크기는 10만, 100만, 1,000만, 1억 건이다.
- 검색어는 상품명 일치 비율 등급에 걸친 9개다. high 강아지(50%), mid 사료, 연어, 간식(6.7%에서 10%), low 관절, 하네스, 바잇미(2.5%에서 3.3%), rare 한정판(0.1%), none 없는상품(0%)이다. T14부터 상품명 어휘에서 뽑은 300개 구성도 쓴다.
- 요청 구성은 반복의 60%가 인기순 첫 페이지, 20%가 가격 필터 낮은 가격순 첫 페이지, 20%가 인기순 첫 페이지 뒤 다음 페이지 둘까지다. 모든 요청은 비로그인 검색이다.
- 셀은 넷이다. ramp는 2 req/s부터 256 req/s까지 45초씩 올리며 첫 페이지 p95 500ms 미만, 실패율 1% 미만, dropped 0을 지킨 마지막 단계를 최대 안정 요청률로 낸다. steady는 기준 요청률의 70%로 3분씩 세 번 돌리고 세 값의 범위가 겹치지 않을 때만 차이로 본다. 순간 부하는 기준 요청률의 3배를 30초 보낸 뒤 탐침으로 회복 시간을 잰다. T13부터는 steady 안에서 ES를 30초 멈추거나(`docker pause`) ES 응답을 60초 동안 1초 늦추는(`tc netem`) 장애 셀과 DB만 읽는 대조 요청(비로그인 상품 상세, 초당 2건)을 더했다.
- 단계마다 한 가지를 바꾸고 전과 후를 같은 세션, 같은 데이터, 같은 부하로 재는 것을 원칙으로 했다. 예외가 있다. T06과 T16은 여러 변경을 함께 넣었고 T10은 레버를 하나씩 더해 쟀지만 기준은 앞 세션에서 잰 T08이다. 속도보다 결과가 같은지를 먼저 봤고 효과가 없던 단계(T02)도 남겼다.

- T09(ES 전용 기능 시연)는 하지 않았다.
- T10의 레버는 다섯 개다. 낮은 가격순을 할인 중인 상품과 아닌 상품의 필드 정렬 요청 둘로 나눴다. 색인을 id 내림차순으로 정렬해 두었다. 첫 페이지 총개수를 크기 0 요청으로 따로 보내 샤드 요청 캐시가 재사용하게 했다. 결과 요청은 개수를 세지 않는다. 할인 조건을 `must_not` 대신 OR로 걸렀다.

## 100만 건 여정

| 단계 | 엔진 | steady 요청률 | 첫 페이지 p95 | 최대 안정 요청률 |
|---|---|---|---|---|
| T01 기준 jar | MySQL | 0.175 req/s | 9,842ms | 0 |
| T06 jar | MySQL | 2.8 req/s | 814ms에서 820ms | 0 |
| T07 jar | Elasticsearch | 2.8 req/s | 25ms | 256 req/s |

- 세 줄은 서로 다른 날의 세션이고 T01은 부하도 다르다. 기준 jar는 0.25 req/s에서도 SLO를 지키지 못해 steady를 그 70%로 돌렸다. 차이가 수백 배라 세션 차이로 결론이 바뀌지 않는다고 보고 한 세션으로 다시 재지 않았다.

## 1,000만 건 최종 비교(T11)

T11은 같은 날 jar마다 새로 색인하고 같은 조건 순서로 T07 jar와 최종 jar를 쟀다. ES 호스트는 m7g.large이고 조건마다 steady(22.4 req/s, 180초)를 세 번 돌렸다.

| 조건 | 첫 페이지 p95, T07 jar | 첫 페이지 p95, 최종 jar | 중앙값의 비 | 최종 jar 요청 캐시 적중률 |
|---|---|---|---|---|
| 고정 검색어 9개 | 164에서 290 | 17에서 20 | 9.8배 | 66.6%에서 66.7% |
| 검색어 300개 | 296에서 353 | 62에서 67 | 4.9배 | 60.2%에서 66.6% |
| 고정 9개와 쓰기 초당 10건 | 168에서 1,396 | 24에서 39 | 7.0배 | 25.7%에서 26.1% |
| 검색어 300개와 쓰기 초당 10건 | 127에서 147 | 36에서 79 | 3.6배 | 0.0%에서 0.3% |

- 완성된 두 구현의 조건부 비교다. 시간과 순서의 영향을 없애지 못했고 두 색인의 세그먼트 배치도 다르다. 재시작 뒤 확인이 측정 전에 정한 기준을 벗어나 최종 jar를 새 색인에서 다시 쟀고 다시 잰 값은 밤 값과 같은 범위였다.
- 쓰기 셀에서는 세그먼트가 쌓이다 큰 병합이 일어난 run의 꼬리 지연이 컸다(T07 jar 첫 페이지 p95 1,396ms).
- 요청 캐시를 끈 최종 jar(밤, 고정 9개)는 첫 페이지 p95가 18ms에서 19ms로 그대로였다. 두 jar 차이 중 요청 캐시의 몫은 나누지 않았다.
- 쓰기 셀이 끝난 뒤 최종 jar 검색어 300개를 쓰기 없이 다시 재자 첫 페이지 p95가 62ms에서 67ms가 27ms에서 32ms로 낮았다. 앞 셀들이 남긴 상태(병합된 세그먼트, 채워진 노드 쿼리 캐시)나 시간의 영향과 맞고 무엇 때문인지는 나누지 못했다. 쓰기 셀과 그 뒤 값에는 순서의 영향이 섞인다.

## ES 장애 대응(T13, T16)

T13과 T16은 다른 세션과 다른 ES 호스트에서 쟀다. 각 단계 안의 전과 후만 비교한다.

| 단계와 호스트 | 셀 | 지표 | 전 | 후 |
|---|---|---|---|---|
| T13, r7g.xlarge | ES 정지 30초 | 정지 구간에 응답이 끝난 상품 상세 p95, DB 커넥션 대기 최대 | 19.9초에서 21.1초, 190에서 191 | 6ms에서 11ms, 0 |
| T13, r7g.xlarge | ES 응답 1초 지연 | 지연 구간 상품 상세 실패 | 60건 안팎 중 17건에서 24건 | 120건 중 0건 |
| T16, m7g.large | ES 응답 1초 지연 | 지연 구간 검색 성공 비율, ES가 받은 쿼리 | 4%에서 5%, 초당 0건 | 82%에서 85%, 초당 37건 |
| T16, m7g.large | ES 정지 30초 | 정지 구간 실패 응답 p95 | 3,004ms에서 3,008ms | 4ms에서 8ms |
| T16, m7g.large | 129 req/s 순간 부하 30초 | 첫 페이지 p95, 상품 상세 p95, 처리 중 요청 최대 | 1,948ms, 693ms, 200 | 235ms, 87ms, 21 |

- T13 전에는 검색 Facade의 읽기 트랜잭션이 ES 호출까지 포함해 ES를 기다리는 동안 DB 커넥션을 반납하지 않았다. ES가 멈추면 검색이 커넥션 10개를 모두 쓰고 Tomcat 스레드 200개가 커넥션을 기다려 DB만 읽는 요청도 멈췄다.
- T13 뒤에는 ES 응답이 1초 늦을 때 검색이 거의 모두 실패했다. 원인은 검색 응답 대기 상한 3초가 ES 클라이언트 연결(기본 10개)을 기다린 시간까지 센 것이었다. 연결을 기다리던 검색이 3초를 넘겨 요청을 취소하면서 맺는 중이던 연결을 끊었고 지연이 끝날 때까지 연결이 다시 맺어지지 않았다.
- T16은 앱이 동시에 보내는 ES 요청을 연결 수(40) 이하로 두고 자리가 없는 검색은 기다리지 않고 바로 503을 돌려준다. 시간을 넘긴 요청의 취소도 없앴다. 이 변경을 함께 넣은 jar에서 연결이 유지됐고 ES가 지연 중에도 초당 37건을 처리했다. 변경마다 따로 재지는 않았다. 취소하던 버전은 상한 40에서 ES 클라이언트의 I/O 스레드가 멈춰 api를 다시 띄울 때까지 모든 검색이 500이었다.

## 결과가 같은지 확인한 방법

- 코드를 바꾼 단계마다 고정 요청 384개(검색어, 정렬, 필터, 페이지 조합)의 응답을 이전 단계와 비교했다. MySQL 단계(T02부터 T06)와 ES 어댑터(T07)는 응답이 바이트 단위로 같다. T10은 L1, L2, L4, L5의 고정 요청 응답이 T07과 같고(L3는 따로 비교하지 않았다) JPA 어댑터와 결과를 비교하는 통합 테스트를 더했다. T13과 T16도 고정 요청 응답이 앞 단계와 같다.
- 측정만 한 T08은 비교하지 않았다. 1,000만 건에서 비교할 MySQL 기준 응답을 받지 않았고 재색인 문서 수가 상품 수와 같은지만 봤다.
- T15는 고정 시드로 상품 300개와 검색 200개를 무작위로 만들고 두 어댑터의 커서 페이지를 끝까지 비교하는 테스트다. 탐색 실행에서 시드 18개와 시드마다 검색 300개(모두 5,400건)를 돌렸고 차이가 없었다. 알려진 정렬 규칙 차이(악센트, 전각 문자)를 넣으면 시드마다 7개에서 8개 검색이 실패해 차이를 잡는 것을 확인했다.
- 1억 건(T12)은 동등성을 확인하지 않았다. T07 jar가 높은 일치 검색어에서 3초 시간 초과라 비교할 응답이 없었다.

## 한계

- 상품명과 검색어가 합성이다. 고정 검색어 9개는 ES 요청 캐시 적중률을 실제보다 높인다. T14와 T11에서 검색어 300개와 쓰기 부하 조건으로 결과가 얼마나 바뀌는지 봤다. 이 조건은 캐시 적중만이 아니라 쿼리 구성, 세그먼트, 병합, 색인 작업도 함께 바꾸므로 캐시의 몫을 따로 잰 것은 아니다.
- 첫 페이지의 결과 요청과 개수 요청은 따로 나간다. 실제로 결과가 바뀌는 쓰기가 들어오면 두 요청이 서로 다른 refresh 시점의 색인을 볼 수 있다. 쓰기 부하 셀은 같은 내용을 다시 넣어 이 경우가 생기지 않았다(T14).
- 실시간 색인 동기화가 없다. 색인은 마지막 재색인 시점의 데이터다. 쓰기 부하 셀은 같은 내용의 문서를 다시 넣어 refresh와 캐시 무효화만 만든다.
- ES는 단일 노드이고 복제가 없다. 노드 장애는 정지와 응답 지연으로만 쟀다. 응답 지연 셀은 연결 수립 패킷까지 늦춘다.
- ramp와 순간 부하는 변형마다 대부분 한 번씩 돌렸다. steady만 세 번이다.
- 단계는 2026-10-15부터 11-08까지 여러 세션에 걸쳐 있다. 같은 jar도 ES 호스트에 따라 크게 다르다. T13 jar의 96 req/s 순간 부하 첫 페이지 p95는 r7g.xlarge에서 486ms, m7g.large에서 59ms였다. T07 jar의 steady 첫 페이지 p95는 T08(m7g.large)에서 80ms, T14(r7g.xlarge)에서 191ms에서 212ms, T11(m7g.large)에서 164ms에서 290ms였다. 같은 m7g.large에서도 느렸으므로 호스트만으로는 설명되지 않는다. T08과 비교해 노드 쿼리 캐시 메모리와 세그먼트 수가 달랐지만 원인으로 확인하지는 않았다. r7g.xlarge는 ES 쿼리 하나에 호스트 CPU를 20%에서 35% 더 썼고 이유는 확인하지 않았다.
- k6 요청은 모두 비로그인이다. 로그인 사용자 경로(찜 조회, 최근 검색어)는 통합 테스트로만 확인했다.
- 첫 페이지의 정확한 총개수는 계약이라 남겼다. 비용의 큰 몫이 여기서 나온다.
